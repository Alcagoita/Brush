## 1. Eighteen rows served the retired `drinks` subtype

**Not a live writer.** Traced 2026-09-28:

* KAN-432 renamed the subtype `drinks` → `wine_and_spirits` in commit
  `0dc0aee`, dated **2026-09-05**, and carried the data across with migration
  `0037`, which lists **791 explicit ids**. Production held exactly 791 rows
  at `wine_and_spirits`, so the migration did precisely what it listed.
* The 18 stragglers were promoted on **2026-09-04** — the day before — and
  their `promotion_note` still reads "reviewed **Drinks** batch: garrafeira",
  the pre-rename batch name. None of the 18 appears in 0037's list.
* Every mapping that feeds the served set says `wine_and_spirits` today:
  `overtureCategories.json`, `venueWords.json`, the reviewed overrides. The
  only file still mentioning `drinks` is
  `extraction/apply_kan411_types.py` (KAN-411), which writes to the retired
  legacy `poi_attribute` table — 0 rows there carry it.

So the defect was an id list that could miss rows, not code that keeps
writing the old value.

**Migration `0050_finish_drinks_rename.sql`** does the same rename by
**value**, which cannot miss a row, across `overture_poi_attribute` and
`curated_poi_attribute`. Applied to production:

```
overture_poi_attribute  store_kind = 'drinks'            18 -> 0
overture_poi_attribute  store_kind = 'wine_and_spirits' 791 -> 809
curated_poi_attribute   store_kind = 'drinks'             0 -> 0
```

Re-runnable: a second apply matches nothing.

Verified through `POST /poi/nearby` at 41.17442345120465, -8.545903026394946:
`Frutaria e Garrafeira da Venda Nova` → `store`, `store_kind:
['wine_and_spirits']`, `country_code: "PT"`. It answers a

A test guards the other half: no committed mapping that feeds the served set
may emit a retired `store_kind` again, or the next promotion reintroduces

## 2. The checker reported five correct rows as lost

`verify_refresh_overrides.compare` compared the override's raw strings
against `primary_poi_type`. Two things were wrong with that:

* **Vocabulary.** An override names types in the classifier's vocabulary, and
  `decide()` resolves them through `reachable_types()` before serving —
  `gas_station` lands on `gas`, `grocery_store` on `supermarket` (KAN-398).
  The checker now resolves through the same function rather than a
  hand-written alias list, so it cannot drift from the promoter.
* **Arity.** KAN-455 allows `poi_type` to be a ranked list. `Opticalia
  Farmacia Silveira` is served as `pharmacy` **and** `store` with
  `store_kind = eyewear_and_optician`, exactly as reviewed; comparing a list
  against a scalar reported it lost. The checker now reads every served type
  from `overture_poi_type` and requires all of them, with rank 0 still
  required to match the first name — a reordered list is a real loss,
  because rank 0 is what the app shows.

The rows involved — `43bd621a` (`gas_station`→`gas`), `621ac9b7` and
`835e1e64` (`grocery_store`→`supermarket`), `c8761ae1` and `fd7cbee5`
(`['pharmacy','store']`) — were correct in production throughout. Nothing
about them was changed.

Reads stay bounded: the served-types lookup is a third read per batch of
≤ 150 ids, alongside the candidate join and the attributes.
