# KAN-474 — run record, 2026-10-03

A place has one name per language of its country, so Portugal has **two**
choices, not one:

| choice | shows | PT |
|---|---|---|
| `native` — "Country native" | `name_local` where recorded, else `name` | Portuguese throughout |
| `source` — "As I found it" | `name` as the source supplied it | Portuguese mostly, English for ~1% |

A country with two native languages offers `source` plus one choice per
language; `native` is not offered there, because "the country's language" does
not name one of two.

## What changed

* `poiName.placeNameOptions` decides the shape. One language (or none) gives
  `['native', 'source']`; two or more give `['source', …languages]`.
* `selectPoiName` has a declared `'source'` choice returning `name`. It used to
  reach the same answer by falling through every other branch — right
  behaviour, undeclared intent. Asking for the language that `name_local_lang`
  records now returns `name_local`, which is what makes a per-language choice
  work in a two-language country.
* Settings is disabled only when **no country resolves**. The old test was
  `languages.length <= 1`, which disabled the control for every PT user — the
  bug that kept the 315 names from KAN-471 from being switchable.
* Copy, owner's wording: **"As I found it"** / **"Como encontrei"**.
* `/poi/name-languages` reads `src/countryLanguages.json` instead of
  `overture_country_import.name_languages_json`. That field is scanned out of
  the Overture archive, and Overture carries no language variants at all, so it
  was NULL and always would be. A country's languages are a fact about the
  country, not about what a data release happened to include.
* Migration `0057`: `curated_poi.names_json`. `overture_poi` already had it;
  `curated_poi` was the only served table without one, so a curated row in a
  two-language country could not have held its second name. The Worker now
  selects and returns it, so **a two-language country needs no schema change —
  only a config entry.**
