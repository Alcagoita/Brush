# KAN-474 — run record, 2026-10-03

A place has one name per language of its country, so Portugal has **two**
choices, not one:

| choice | shows | PT |
|---|---|---|
| `native` — "Country native" | `name_local` where recorded, else `name` | Portuguese throughout |
| `source` — "As I found it" | `name` as the source supplied it | Portuguese mostly, English for ~1% |

A country with two native languages adds one choice per language on top, so a
user can ask for one by name. `native` is offered there too and still means
`name_local`, whichever language `name_local_lang` records it in — it is the
default, so leaving it out would mean a user who has chosen nothing has no
option selected and a Settings row labelled with something the picker never
offered.

## What changed

* `poiName.placeNameOptions` decides the shape: always `['native', 'source']`,
  plus one entry per language where a country has two or more.
  `defaultPlaceNameChoice` is shared by `selectPoiName`, the Settings row and
  the picker's selection, so all three agree on what is shown when the user has
  chosen nothing.
* `selectPoiName` has a declared `'source'` choice returning `name`. It used to
  reach the same answer by falling through every other branch — right
  behaviour, undeclared intent. Asking for the language that `name_local_lang`
  records now returns `name_local`, which is what makes a per-language choice
  work in a two-language country.
* Settings is disabled only when **no country resolves**. The old test was
  `languages.length <= 1`, which disabled the control for every PT user — the
  bug that kept the 315 names from KAN-471 from being switchable.
* Copy, owner's wording: **"As I found it"** / **"Como encontrei"**.
* `/poi/name-languages` reads `src/countryLanguages.json` instead of
  `overture_country_import.name_languages_json`. That field is scanned out of
  the Overture archive, and Overture carries no language variants at all, so it
  was NULL and always would be. A country's languages are a fact about the
  country, not about what a data release happened to include.
* Migration `0057`: `curated_poi.names_json`. `overture_poi` already had it;
  `curated_poi` was the only served table without one, so a curated row in a
  two-language country could not have held its second name. The Worker now
  selects and returns it, so **a two-language country needs no schema change —
  only a config entry.**

## `name_en` removed from every code path

The owner asked why it was kept at all. There was no reason, and the two
hesitations I had both turned out to be wrong:

* **"The code consults it."** It did — `selectPoiName` read it as
  `legacyEnglish` in two branches — but it is NULL on all 215,994 Overture
  rows and all 9,978 curated rows, and always would be: Overture carries no
  language variants, so nothing ever filled it. Logic that can only ever
  return `null` is not a fallback, it is a dead branch.
* **"Removing it is a device migration."** It is not. The offline cache adds
  these columns with an additive `ALTER TABLE` loop and inserts by explicit
  column list, so the code can stop writing and reading a nullable column
  without touching an installed database. A device that already added it
  keeps it, unused, until the cache is rebuilt.

Gone from: the Worker's two SELECTs, both row builders, the duplicate-name
set and the wire (`cloudflare/src/index.ts`); the app's response type,
`NearbyPlace`, `PlaceCandidate`, the offline insert/update/readers and the
trip export; `selectPoiName`'s parameter and `displayPlaceName`'s call; and
the extraction pipeline — the DuckDB scan no longer selects
`map_extract(names.common, 'en')`, and the loader, promoter, refresh and
Place export no longer carry the column. The refresh's `name_en = COALESCE(…)`
guard went with it; the `name_local_source` guard that protects KAN-471's 315
reviewed names is unchanged and still asserted.

**The D1 columns stay** on `overture_poi`, `overture_candidate` and
`curated_poi`, annotated as dead in `schema.sql`. Cleanup means code paths,
never data, and dropping an empty column nothing reads buys nothing.

No wire-compatibility concern: the field was optional in the app's type and
null on every row, so a client reading it got `null` before and gets
`undefined` now — same rendered name either way.
